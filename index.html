AI-Driven Development Life Cycle, AI-DLC (Jul 2025; FS post May 2026)
Lifecycle shapeBaseline

Six stages (Plan, Design, Build, Test, Deploy, Maintain) run as a loop, not a line. Stages are modular; adopt them in any order your dependencies allow.

Plays overview ↗
Similar

Three phases (Inception, Construction, Operations). Operations feeds production learning back into the next Inception cycle, so it is also a loop.

How AI-DLC works ↗
Handoff between stagesBaseline

Each stage commits a named file (intent.md, spec.md, plan.md, the diff, review findings, incident record). The next stage starts by reading it. The commit chain is the audit trail.

The shifts across stages ↗
Similar

AI stores plans, requirements and design artifacts in the project repository so work continues across sessions. Artifact names are not standardised in the posts reviewed.

How AI-DLC works ↗
Encoding institutional rulesBaseline

CLAUDE.md for conventions, skills for policies applied consistently, hooks for rules that must always hold. All version controlled and reviewed like code.

Build stage ↗
Similar

Steering files guide the agent on security policy, architecture standards, approved dependencies and regulatory guidance. Implemented through Amazon Q project rules and Kiro workflows.

AI-DLC for Financial Services ↗
Deterministic enforcementBaseline

Hooks block or gate actions deterministically (protected paths, test-file edits, production deploys). Managed settings stop engineers switching them off.

Hooks as approval gates ↗
Different path, same outcome

Enforcement is described mainly as automated quality gates in the CI/CD pipeline and steering files. No equivalent of per-action hooks appears in the posts reviewed.

AI-DLC for Financial Services ↗
Role of the humanBaseline

Humans review at gates and judge intent and risk. Agentic review layers run first; human review is reserved for regulated and critical code.

AI in the PR review loop ↗
Different path, same outcome

Humans validate each AI plan and decision before execution proceeds. The AI plans, asks clarifying questions, and implements only after human validation, repeated for every activity.

How AI-DLC works ↗
Risk-based approvalBaseline

Autonomy is tiered by environment and risk. Agents act freely in dev, prepare the release in production, and a named person authorises it.

CI/CD integration ↗
Same

Risk-based change categorisation: only material changes need human sign-off, routine changes flow through automated validation. Production and high-impact actions keep approval controls.

AI-DLC for Financial Services ↗
Testing and self-verificationBaseline

Every session verifies its own work (tests, build, screenshot diff) before a human sees it. Continuous evals regression-test the agent configuration itself.

Test stage ↗
Similar

AI validates its own work and self-corrects when tests fail, including deviations from steering files. QA is left-shifted, with high-fidelity test environments and security testing.

AI-DLC for Financial Services ↗
Closing the loop after releaseBaseline

Headless stage: a deterministic detector watches production metrics against control bands and invokes the agent, which writes the finding as a new intent.md. Scheduled security scans and Slack-based on-call extend it.

Maintain stage ↗
Different path, same outcome

Monitoring feeds the coding agent's context and informs future Inception cycles. AI agents (for example Amazon DevOps Agent) can investigate incident root causes. Less specific on autonomy tiers.

AI-DLC for Financial Services ↗
Team structure and ritualsBaseline

Not prescribed. Focus is on artifacts, automation and gates. One engineer can run several parallel sessions, but no new team model or vocabulary is mandated.

Parallel sessions and subagents ↗
Completely different

Prescriptive. AI Pods of 2 to 3 developers replace scrum teams of about 7. Sprints become "bolts", epics become Units of Work, and Mob Elaboration / Mob Construction are team rituals. Co-location matters in Inception.

How AI-DLC works ↗ Organizational shift ↗
MeasurementBaseline

Each play names a leading and a lagging indicator, mostly read from git history, PR metadata and CI events (for example time from intent to spec, rework after build starts, DORA).

How to measure it (per play) ↗
Different path, same outcome

A KPI suite (mean time to deploy and recover, failed-deployment %, incidents by severity, technical debt, NPS) plus Amazon's Cost-to-Serve-Software framework for the financial case.

Closing thoughts ↗
Completely different

Quotes figures: a Bedrock engine rebuilt by 6 engineers in 76 days against an estimate of 40 engineers for a year, and an unnamed European bank going from 12 to 3 developers. All vendor-reported.

A signal too big to ignore ↗
Strengths (our assessment)
  • Concrete and implementable: named files, example configs, prompts
  • Controls are deterministic (hooks, managed settings), not just advisory
  • Every play has measurable indicators drawn from existing tooling
  • Modular: start with any no-prerequisite play
  • Clear operating model for teams (AI Pods, mob rituals)
  • Strong regulated-industry story: traceability, steering files, risk-based approval
  • Business-case framing (cost-to-serve) for executives
  • Workflows are open-sourced; the FS post names Claude Code alongside Kiro
Gaps and watch-outs (our assessment)
  • Tooling is Claude-centric; other agents need translating
  • Says little on team structure, roles and change management
  • No baseline step before the loop; third-party critics flag measurement needs a pre-existing baseline
  • No customer outcome numbers to anchor an ROI case
  • Headline results are vendor-reported or unnamed
  • Public posts are conceptual; detail sits in a whitepaper
  • Heavy rituals and co-location may be hard to retrofit onto existing teams
  • Slower on autonomous operation: humans stay close to every plan
