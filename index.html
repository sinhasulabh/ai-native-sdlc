AI Native SDLC: Intent based Development

How work moves from a user signal to verified value in production when AI does the building and humans hold the decisions.

Purpose and scope

This document defines a target flow for AI-native software delivery: how work moves from a user signal to verified value in production when AI does the building and humans hold the decisions.

The flow was designed from first principles, without the constraints of today's process (sprints, ticket types, role titles). It is an attempt to reinvent the SDLC flow for an AI-native world, rather than to adapt today's process.

It is a design model, not a tool selection, an adoption plan or a replacement for an organisation's risk and compliance policy. Where the design deliberately leaves a choice to teams, the document says so and lists it under open points. Overlaying a specific organisation's real-world constraints on this flow is a separate, later step.

Design principles

Six principles shape every choice in the flow.

  1. North star: time from user signal to verified value in production, with quality held constant. A shortcut that trades correctness for speed does not count.
  2. The unit of work is an intent: an outcome plus how it will be verified. Stories describe activity; intents describe outcomes, so what enters the flow already carries its own verification.
  3. AI suggests, humans decide. AI collects signals, drafts intents, builds, checks and recommends. Humans decide at defined gates.
  4. Autonomy is earned per category of intent. Every category starts with full human review. Agreement between AI and human, and delivered outcomes, decide when a category gets more autonomy.
  5. Deploying is separate from releasing. Every change that can be flagged ships behind a flag, off by default, so it can be reversed without a redeploy.
  6. Every closed intent teaches the system. Each one writes a structured record that feeds autonomy decisions and turns missed issues into new rules and tests.

The target flow at a glance

Humans hold six gates; everything between them is AI or automation.

Gate 4 applies only when a guardrail is breached, and Gate 5 only to irreversible data-migration steps. Closing an intent returns outcomes and lessons to intake, which is what lets each category earn more autonomy over time.

Intake and prioritisation

AI drafts and ranks candidate intents, and a human decides which go ahead. The ranking formula is the team's choice, applied to a fixed set of inputs.

Signals (user feedback, telemetry, support tickets, incidents) are collected continuously. AI clusters them and drafts candidate intents, each with an outcome and a verification. Gate 1 is the human decision on which intents proceed.

Fixed inputs. Every intent carries the same five inputs, whatever formula the team uses.

InputMeaningExample
ValueReach and impact40,000 users per month, +5% conversion
ConfidenceHow sure the estimate is70%
RiskBlast radius if it goes wrongMedium (touches checkout)
CostHuman review hours, not build time3 review-hours
UrgencyHow fast the value decaysNone

Cost means review load because AI makes build effort much smaller, though not uniform: complex changes still cost more iterations, compute and verification. The scarce resource is human attention.

Configurable formula. Teams choose the prioritisation framework that suits them. Common options include RICE, ICE and WSJF, as well as MoSCoW, the Kano model, value-versus-effort matrices and weighted scoring, or a custom formula over the same fixed inputs. WSJF is the suggested default. The inputs, score and rationale are stored with every intent so the ranking can be compared with the human's decision later.

Build and verification

Nothing is built until a human has approved the spec and its verification plan, and nothing merges until the same checks have run twice: in the agent loop and in CI.

  1. Gate 2, the spec gate. A human approves the spec and the verification plan: functional tests derived from the spec, the rollout plan and the guardrail thresholds. The approved tests are the contract. The builder does not write its own tests after the fact, because the same misunderstanding could then sit in both the code and the tests.
  2. Hooks in the agent loop. Deterministic checks run at lifecycle points (tests, types, security, policy) and block the agent early.
  3. The same checks in CI. They run again on the finished code, so a misconfigured or bypassed hook cannot let a change through. Hooks give early feedback; CI gives the guarantee.
  4. A scope-drift gate. It flags changes outside the files and behaviour the spec names, such as an unrequested edit.
  5. Flag combination tests. Flags in the same area can interact, so their combinations need testing, and the number of combinations grows as 2^N. How much to test, and how many child flags a master flag carries, is left to teams.
  6. Gate 3, human PR review. The reviewer receives a report: gate results, the scope check, a mapping from the change to the spec, and an AI first-pass summary. Every PR goes to a human for now.

Code conflicts between intents are resolved before merge, by rebasing and re-verifying. A merge that is clean as text can still break behaviour, which is why the combination tests matter. The gates check rules and the approved tests; the human review covers what they cannot, such as UX feel and maintainability.

Release and rollback

Every change that can be flagged ships behind a flag, off by default, and a human decides whether to roll back.

  • A flag on every flaggable change, including changes with no functional impact. Performance, memory and dependency effects can still break production, and one uniform rule keeps the flow simple.
  • Staged, rule-based ramp. The rollout plan sits in the approved spec, for example internal users, then 1%, 10%, 50% and 100%. Automation advances a step only while the guardrail metrics hold.
  • On a guardrail breach the AI pauses the ramp, then recommends turning the flag off, holding or continuing, with the evidence. A human decides (Gate 4) and the AI executes. If nobody responds, the ramp stays paused and the alert escalates. Turning a flag off reverts code paths, not data: anything the new path wrote, and sessions already in progress, survive it.
  • Concurrent intents in one area ship under one master flag with independent child flags, to the same cohort. Any child can be turned off without affecting the others. Teams plan the combination testing, and each intent records its attribution method.
  • Changes that cannot be flagged get a named alternative. Data migrations run in canary cycles using expand-contract, which keeps the schema reversible until the final step that drops old data; that step needs a human (Gate 5). Dual-write and backfill steps can still damage data before then, so each canary cycle verifies the data, not only the code. Security fixes ship immediately to everyone, with rollback kept and the same gates run at urgent priority. Rolling one back reopens the vulnerability, so the Gate 4 decision for a security fix includes someone accountable for security. Dependency and runtime upgrades go through a canary rollout.

Permanent flags, such as kill switches and entitlements, are typed as permanent and stay in the fully-on state. Only temporary release flags reach cleanup.

Closing the loop and learning

An intent is done only when its outcome metric is verified in production, and every closed intent leaves a record the system learns from.

  • Closing rule. The metric named in the intent must move as promised over the verification window. If it does not, the result returns to intake as new signal.
  • Attribution method, recorded per intent. Split the cohort so each change has its own group, or stagger the releases. Either can add a holdout group (5 to 10%) that gets none of the changes. Teams choose. Staggering compares before and after, so seasonality can distort the result.
  • A structured record per closed intent: the AI's recommendation, the human's choice and the reason when they differ, the outcome against the promised value, and lessons.
  • Two measures per category of intent. Agreement: how often the human accepted the AI's recommendation. Outcome: whether approved intents delivered the value they promised. Agreement alone can mislead if reviewers rubber-stamp, so a category gains autonomy only when both hold. Outcome data also calibrates the AI's value estimates.
  • Misses become rules. When a gate missed something or a human caught it, the case becomes a new rule or test.
  • Automated flag removal. Closing the intent triggers a flag-removal change that passes the same gates. Temporary release flags are removed. Permanent flags (kill switches, entitlements) are typed as such and stay. A flag that ended permanently off has its new code path removed instead.

Human gates

Humans decide at six gates, and a gate is a decision point, not a role: whoever is eligible can pass it. Each gate is defined by four fields, so a team can configure it without inventing new roles. Anyone may decide, but every gate names who is accountable for the outcome.

The escalation chain (who is alerted first, how long before the next person, who is the final owner) is left for each team to define.
